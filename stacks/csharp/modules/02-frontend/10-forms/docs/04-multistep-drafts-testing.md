# Multi-step forms, drafts, and testing
[← Overview](00-overview.md)

## Why it matters
- A three-step checkout loses everything when the user goes back from payment to fix the address.
- A long B2B order form times out the session; the customer loses 20 minutes of input.
- A refactor of the form's error mapping silently breaks server error display; no test covered a 400 response.

## Concepts

### Multi-step forms
| Decision | Options |
|:--|:--|
| state | one `useForm` across steps (simplest), or one form per step + a store/reducer for completed steps |
| validation per step | `trigger(["street", "postalCode"])` before "Next", or one schema per step |
| URL per step | `/checkout/address`, `/checkout/payment`: Back button works, analytics per step |
| server-side progress | the API stores the checkout draft (cart → shipping → payment), so steps survive reloads and devices |
| accessibility | step indicator with `aria-current="step"`, focus the step heading on change, announce "Step 2 of 3" |

For a shop checkout, the API owns the checkout state (address chosen, shipping method) as part of the cart; each step is a small form that saves to the API.

### Draft persistence
| Draft store | Use | Watch out |
|:--|:--|:--|
| API (server draft) | important, cross-device (checkout, long applications) | autosave endpoint, debounced |
| `localStorage`/`sessionStorage` | convenience for long forms on one device | never store payment data or passwords; clear on submit |
| `beforeunload` warning | unsaved changes | use sparingly |

Autosave: `watch` (or `useWatch`) → debounce 1–2 s → save → show "Saved at 14:02" in a status region.

### Testing forms
| Level | Tool | Checks |
|:--|:--|:--|
| ⭐ component | Vitest + Testing Library + `user-event` | labels, validation messages, submit payload, disabled states |
| network | ⭐ MSW | success, 400 `ValidationProblemDetails`, 409, 500 responses from "the API" |
| schema | plain Vitest | Zod schema edge cases (generated + extensions) |
| E2E | Playwright (13-testing-monitoring) | the real checkout against a test API |

Query by role and label (`getByRole("textbox", { name: "Postal code" })`), type with `user-event` (realistic events), assert visible text, not RHF internals. MSW handlers can be generated by Orval (`mock: true`), then overridden per test for error cases.

## Example
`web/src/features/account/NewAddress.test.tsx`
```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";
import { QueryClient, QueryClientProvider } from "@tanstack/react-query";
import { NewAddress } from "./NewAddress";

const server = setupServer();
beforeAll(() => server.listen({ onUnhandledRequest: "error" }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

const renderForm = () =>
  render(<QueryClientProvider client={new QueryClient()}><NewAddress /></QueryClientProvider>);

test("shows the API's validation message on the postal code field", async () => {
  server.use(http.post("*/api/me/addresses", () =>
    HttpResponse.json({ status: 400, title: "One or more validation errors occurred.",
      errors: { PostalCode: ["We don't deliver to this postal code yet."] } },
      { status: 400, headers: { "Content-Type": "application/problem+json" } })));
  const user = userEvent.setup();
  renderForm();

  await user.type(screen.getByRole("textbox", { name: /full name/i }), "Ada Lovelace");
  await user.type(screen.getByRole("textbox", { name: /street/i }), "Kahve Sk. 1");
  await user.type(screen.getByRole("textbox", { name: /postal code/i }), "99999");
  await user.type(screen.getByRole("textbox", { name: /city/i }), "Istanbul");
  await user.click(screen.getByRole("button", { name: /save address/i }));

  const postal = screen.getByRole("textbox", { name: /postal code/i });
  expect(await screen.findByText("We don't deliver to this postal code yet.")).toBeVisible();
  expect(postal).toHaveAttribute("aria-invalid", "true");
});

test("blocks submit and explains a missing city", async () => {
  const user = userEvent.setup();
  renderForm();
  await user.click(screen.getByRole("button", { name: /save address/i }));
  expect(await screen.findByText("Enter the city")).toBeVisible();
});
```
Step validation in a multi-step form:
```tsx
async function next() {
  const ok = await form.trigger(["street", "postalCode", "city"]);
  if (ok) { await saveShippingStep(form.getValues()); router.push("/checkout/payment"); }
}
```

## Production patterns
- Checkout state lives in the API; each step saves, so reloads and device switches are safe.
- Drafts never include payment data; local drafts are cleared on success.
- Every form has tests for: valid submit payload, client validation messages, server 400 mapping, server 409/500 messages.
- MSW in development too (optional), so frontend work isn't blocked by API changes.

## Mistakes
Wrong: testing implementation details.
```ts
expect(form.formState.errors.city).toBeDefined();
```
Right: assert what the user sees (`findByText("Enter the city")`, `aria-invalid`).

Wrong: separate forms per step with no persistence; Back loses data.
Right: one form across steps, or save each step to the API.

## Check yourself
1. How do you validate only the current step's fields in React Hook Form?
2. What should never go into a local draft?
3. Why test the 400 response path with MSW?

<details><summary>Answers</summary>

1. `trigger([...fieldNames])` before moving on (or a per-step schema).
2. Payment data, passwords, one-time codes, and other secrets or sensitive personal data.
3. It's the contract with the C# API's `ValidationProblemDetails`; without a test, changes to mapping or keys break silently.
</details>
