# Code review, dead code, and tech debt
[← Overview](00-overview.md)

## Why it matters
- A method named `Process` takes a `bool` and an `int` and does five things. Every change to it causes a bug somewhere.
- The solution has 14 unused NuGet packages; two of them have known vulnerabilities and fail the audit gate.
- A codebase with 3,000 suppressed warnings can't turn on any new rule, because nobody knows which suppressions are real.

## Concepts

### Code review standards
| Area | Look for |
|:--|:--|
| naming | `PascalCase` types/members, `camelCase` locals/params, `_camelCase` private fields, `Async` suffix on async methods, `I` prefix on interfaces |
| size | methods that fit on a screen; classes with one job |
| parameters | no boolean flags that switch behavior (`Process(order, true)`) → two methods or an enum |
| comments | explain **why** (business rule, workaround, link), not what the code says |
| errors | no swallowed exceptions (`catch { }`), no `catch (Exception)` without rethrow/log at the boundary |
| async | `await` all the way, `CancellationToken` passed, no `.Result` |
| visibility | `internal` and `sealed` by default; public only what other projects need |
| tests | new behavior has tests; bug fixes have a regression test |

Comment that earns its place:
```csharp
// Stripe rounds card amounts half-up in minor units; match it so totals reconcile (see ADR-012).
var amount = Math.Round(total * 100m, MidpointRounding.AwayFromZero);
```

### Dead code and dependency hygiene
| Rule / tool | Finds |
|:--|:--|
| IDE0051 / IDE0052 | unused / unread private members |
| IDE0060 | unused parameters |
| IDE0005 | unnecessary usings (needs `GenerateDocumentationFile`) |
| CA1822 | members that could be `static` (often a sign of misplaced code) |
| CA1812 | internal classes never instantiated |
| `dotnet package list --outdated` | outdated packages (.NET 10 noun-first form of `dotnet list package`) |
| `dotnet package list --vulnerable --include-transitive` | known vulnerabilities |
| `dotnet nuget why <project> <package>` | why a transitive package is there |
| `<IsAotCompatible>` / trimming warnings | reflection-heavy dead paths (optional) |

Unused public APIs are harder: analyzers can't know who else calls them. Make types `internal` by default so the compiler can tell you.

Remove packages with `dotnet package remove`. Fewer packages means fewer vulnerabilities, faster restores, and fewer licence surprises (MediatR, AutoMapper, MassTransit, and FluentAssertions all moved to commercial licences recently).

### Managing tech debt
| Tool | Use | Rule |
|:--|:--|:--|
| `#pragma warning disable CA2000 // reason` … `restore` | one spot | always with a reason, smallest scope |
| `[SuppressMessage("Reliability", "CA2000", Justification = "...")]` | one member | `Justification` required in review |
| `GlobalSuppressions.cs` | project-wide, targeted by member | generated by the IDE; review it |
| `.editorconfig` severity per folder | e.g. legacy folder | temporary, with an issue link |
| `<NoWarn>` | whole project | almost never |
| `<WarningsNotAsErrors>` | keep visible, don't fail build | while migrating |
| `#nullable enable` per file | gradual nullable adoption | one folder at a time |
| `<Nullable>warnings</Nullable>` | warnings without annotations | first migration step |

Baselines: when turning on a new rule in an old codebase, record existing violations (suppress them with an issue link), fail only on **new** ones, then burn the list down.

Codemods: Roslyn code fixes with "Fix all in solution", `dotnet format --diagnostics <id>` to apply one fixer everywhere, and the .NET Upgrade Assistant (also seen: GitHub Copilot app modernization) for framework upgrades.

## Example
Turning on a new rule gradually.

`.editorconfig`
```ini
[*.cs]
dotnet_diagnostic.CA2016.severity = error       # forward CancellationToken

[src/Shop.Legacy/**.cs]
# TODO(#311): remove after legacy import is rewritten (target 2026-12)
dotnet_diagnostic.CA2016.severity = warning
```
`terminal`
```bash
dotnet format analyzers --diagnostics CA2016 --severity warn   # apply the code fix where possible
dotnet build -warnaserror                                       # remaining errors show what needs manual work
dotnet package list --vulnerable --include-transitive
dotnet nuget why src/Shop.Api System.Text.Encodings.Web
```
A justified suppression:
```csharp
[SuppressMessage("Reliability", "CA2000:Dispose objects before losing scope",
    Justification = "Ownership passes to the DI container, which disposes it.")]
public static HttpMessageHandler CreateHandler() => new SocketsHttpHandler();
```

## Production patterns
- Reviewers comment on behavior, design, and naming; tools own formatting and mechanical rules.
- Every suppression has a reason; every temporary relaxation has an issue and a date.
- Run `dotnet package list --outdated` and `--vulnerable` monthly (Dependabot does most of it automatically).
- Default to `internal sealed` classes; it makes dead code visible and keeps APIs small.

## Mistakes
Wrong: suppression without a reason, at the widest scope.
```xml
<NoWarn>$(NoWarn);CA2000</NoWarn>
```
Right: fix it, or a scoped `SuppressMessage` with `Justification`.

Wrong: comments that repeat the code.
```csharp
// increment i
i++;
```
Right: comments that explain a decision or a constraint the code can't express.

## Check yourself
1. Why is `internal` by default helpful for finding dead code?
2. What does `dotnet nuget why` answer?
3. How do you turn on a new analyzer rule in a big codebase without stopping all work?

<details><summary>Answers</summary>

1. The compiler and analyzers know every caller of an internal member, so unused ones are reported; public members might be used elsewhere.
2. Which dependency chain brings a (transitive) package into a project.
3. Enable it as an error for new code, relax it (or suppress existing cases with issue links) in legacy areas, and burn the baseline down over time.
</details>
